# Maintenance Notes

These notes are here to keep updates calmer and more consistent.

## 1. Keep source and working layers distinct

If a source-facing file is ugly but faithful, it can stay ugly.

If a working file needs reshaping to become useful, that reshaping should happen there instead of being forced back into the source layer.

## 2. Treat the site and the support system as related but different

The visible app is one job.

The support files behind it are another job.

Both matter, but they should not be confused.

## 3. Prefer teachable structure over archival clutter in working files

When a file is meant to support teaching, phrase work, or future tooling, it should be easy to read and easy to reason from.

That usually means:

- merged overlaps
- clear naming
- consistent examples
- fewer fragments

## 4. Be honest about unfinished parts

The Phrase Builder does not need to pretend to be smarter than it is yet.

The project is stronger when unfinished areas are named clearly instead of papered over with tidy wording.

## 5. Let each docs folder stay local to its job

Top-level docs should explain the whole project.

Phrase Builder docs should explain the Phrase Builder support layer.

This keeps the documentation from becoming one giant undifferentiated pile.
